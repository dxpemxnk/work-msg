# EMS Messenger: учебный разбор проекта

> Актуально для текущего локального проекта `ems-messenger` на 6 октября 2026 года.
> Документ задуман как живая карта проекта: при появлении крупных модулей его стоит обновлять.

## 1. Что мы строим

`ems-messenger` — отдельный локальный сервис корпоративного мессенджера. Он состоит из двух независимых приложений:

- `client` — интерфейс на React;
- `server` — HTTP API, Socket.IO и SQLite.

Проект **не копирует `ems-frontend` и не изменяет его**. Сейчас это самостоятельный стенд для разработки и демонстрации функционала. Позже рабочий `ems-frontend` сможет открывать мессенджер и передавать ему настоящую авторизацию, но этой интеграции пока нет.

Упрощённый поток данных выглядит так:

```text
Пользователь
    ↓
React-компонент
    ↓
useMessenger / RTK Query / Socket.IO client
    ↓
Fastify route или Socket.IO handler
    ↓
Service — бизнес-правила
    ↓
Repository — SQL-запросы
    ↓
SQLite
```

В обратную сторону новые события идут через Socket.IO:

```text
SQLite commit
    ↓
EventPublisher
    ↓
Socket.IO room
    ↓
useMessenger
    ↓
обновление React state и интерфейса
```

### Почему есть `components`, `containers` и `pages`

- `components` получают данные через props и отвечают за небольшой участок UI;
- `containers` соединяют компоненты, hooks, запросы и пользовательские сценарии;
- `pages` дают приложению страницу верхнего уровня.

Пример:

```text
MessengerPage
    ↓ экспортирует
MessengerWorkspace
    ↓ использует
ConversationList + MessageList + MessageComposer
```

## 5. Точка запуска клиента

### `client/src/main.tsx`

Здесь React подключается к элементу `#root` из `index.html`.

Также здесь подключаются:

- `Provider` — делает Redux store доступным всему приложению;
- `ThemeProvider` — передаёт MUI-тему;
- `CssBaseline` — нормализует базовые браузерные стили;
- Roboto — локальный шрифт приложения.

`main.tsx` не содержит бизнес-логики. Его задача — собрать глобальные providers и запустить `App`.

### `client/src/App.tsx`

`App` при старте вызывает `GET /api/v1/me` через RTK Query.

- Если cookie-сессия существует, показывается `MessengerPage`.
- Если сессии нет, показывается `DevLogin`.
- Пока идёт проверка, отображается loader.

Это временный локальный bootstrap. В рабочей интеграции его заменит настоящая схема авторизации EMS.

## 6. Компоненты клиента

Каждая папка компонента содержит:

```text
ComponentName/
├── index.tsx               разметка и поведение
└── index.module.scss       локальные стили компонента
```

SCSS Modules превращают локальное имя класса в уникальное имя при сборке. Поэтому `.item` из одного компонента не конфликтует с `.item` из другого.

### `ConnectionStatus`

Показывает состояние соединения:

- `connecting` — подключение;
- `synchronizing` — восстановление данных после подключения;
- `online` — соединение готово;
- `offline` — соединения нет.

### `ConversationList`

Рисует список бесед слева:

- название;
- последнее сообщение;
- время обновления;
- badge непрочитанных сообщений;
- иконку личной беседы или группы.

Компонент не загружает данные сам. Он получает `conversations`, `selectedId` и `onSelect` через props.

### `ConversationSearch`

Ищет текст по всей доступной истории открытой беседы через серверный API. После выбора результата `MessageList` при необходимости загружает нужный участок истории, прокручивает его к сообщению и временно подсвечивает строку.

### `ConversationDetailsPanel`

Правая панель групповой беседы. Сверху находятся поиск и управление составом группы, ниже — участники с аватарами и индикаторами присутствия. Нажатие на участника открывает компактный `UserProfilePopover` рядом с выбранной строкой.

### `MessageComposer`

Поле ввода сообщения и кнопка отправки.

- Enter отправляет сообщение;
- Shift+Enter добавляет новую строку;
- показывает выбранное сообщение при ответе и позволяет отменить ответ;
- пустое сообщение не отправляется;
- длина ограничена `MESSAGE_MAX_LENGTH`;
- при offline-состоянии поле отключено.

### `MessageList`

Отображает историю и локальные pending-сообщения.

Он отвечает за:

- группировку сообщений по дням;
- расположение своих сообщений справа;
- кнопку загрузки старой истории;
- статус `Отправка…` или `Повторить`;
- одинарную/двойную галочку;
- автоматический scroll к последнему сообщению.
- переход к исходному сообщению из ответа, закрепления или системного уведомления;
- расчёт участников, прочитавших собственное сообщение.

### `MessageItem`

Отрисовывает одно обычное или системное сообщение. Для обычного сообщения показывает автора, аватар, время, статус прочтения, ответ, пересылку, реакции и меню действий. В группах имя автора кликабельно и открывает карточку пользователя.

Системные события распознаются по сохранённому префиксу и показываются отдельной компактной строкой:

- `📞` — результат звонка с зелёной телефонной иконкой;
- `📌` — закрепление с синей булавкой и переходом к оригиналу;
- `👤` — добавление, исключение или выход участника с соответствующей иконкой.

### `MessageReadersDialog`

Показывает, кто прочитал собственное сообщение. Из списка можно открыть личный диалог с участником. Чужие списки прочтения пользователю не раскрываются.

Сохранённые сообщения и локальный outbox объединяются только для отображения. Они по-прежнему имеют разные типы: `Message` и `PendingMessage`.

### `MessageBody`

Отображает текст сообщения и превращает web-адреса в кликабельные ссылки.

Поддерживаются:

- `https://example.com`;
- `http://example.com`;
- `www.example.com`;
- домены без протокола, например `ya.ru`.

Текст не вставляется через `dangerouslySetInnerHTML`, поэтому HTML из сообщения не выполняется. Ссылки открываются с `rel="noopener noreferrer"`.

### `PresenceIndicator`

Зелёная или серая точка и подпись `В сети` / `Не в сети`.

Он ничего не знает про Socket.IO. Компонент получает готовый boolean `online`.

### `UserAvatar`

Показывает инициалы, цвет и размер аватара.

Цвет приходит из БД как динамическое значение. Поэтому SCSS содержит правила отображения, а React передаёт динамические значения через CSS custom properties. Это осознанное исключение: произвольный HEX из БД нельзя заранее записать в статический SCSS-класс без потери гибкости.

### `UserProfilePopover`

Единая компактная карточка пользователя. Она привязывается к нажатому имени или участнику через `anchorEl` и показывает аватар, имя, `@login`, присутствие, кнопки `Написать` и `Позвонить`. Один экземпляр карточки хранится в `MessengerWorkspace`, а не создаётся внутри каждого сообщения.

## 7. Контейнеры клиента

### `MessengerWorkspace`

Главный экран приложения. Он:

- вызывает `useMessenger(currentUser)`;
- собирает sidebar, заголовок, историю и composer;
- хранит текст локального поиска;
- открывает модалки создания беседы и участников;
- управляет Popover закреплённых сообщений и карточкой пользователя;
- запускает личный звонок из карточки пользователя;
- переключает мобильную раскладку;
- показывает общую ошибку в `Snackbar`.

Большая часть сложной логики намеренно вынесена из него в `useMessenger`. Контейнер должен в основном связывать данные и UI.

### `DevLogin`

Временный экран локального входа. Получает тестовых пользователей и создаёт подписанную cookie-сессию.

Он нужен только для демонстрационного проекта. Это не production-аутентификация.

### `CreateConversationDialog`

Formik-форма для:

- личного диалога с одним пользователем;
- группы с названием и несколькими участниками.

Formik хранит состояние формы, Yup проверяет значения, RTK Query отправляет mutation.

### `GroupMembersDialog`

Показывает участников текущей группы:

- имя и login;
- роль владельца;
- presence;
- кнопку перехода в личный диалог.

Кнопка `Написать` вызывает `createDirect`. Сервер либо создаёт новый DIRECT, либо возвращает уже существующий.

### `CallDialog`

Полноэкранный MUI-интерфейс личного звонка.

- для входящего вызова показывает `Ответить` и `Отклонить`;
- для активного вызова показывает микрофон, камеру и завершение;
- для видео выводит удалённый поток и локальный preview;
- для аудио показывает аватар собеседника и воспроизводит remote audio;
- после соединения показывает длительность разговора.

### `PinnedMessagesDialog`

Несмотря на историческое имя, сейчас это MUI `Popover`, привязанный к кнопке-булавке в шапке. Показывает прокручиваемые карточки закреплённых сообщений. Нажатие на текст или автора закрывает Popover и переводит к сообщению; крестик карточки открепляет его. Булавка в шапке окрашивается синим, когда список не пуст.

### `ForwardMessageDialog`

Позволяет выбрать другую доступную беседу и переслать туда сообщение, сохраняя ссылку на автора исходника.

### `GroupCallDialog`

Полноэкранное окно группового аудио- или видеозвонка с плитками участников, локальным потоком и управлением микрофоном, камерой и выходом.

## 8. Главный клиентский hook — `useMessenger`

Файл: `client/src/utils/hooks/useMessenger.ts`.

Это главный координатор клиентской части. Для изучения его лучше делить на несколько зон.

### Данные RTK Query

Hook получает:

- список пользователей;
- список бесед;
- функцию загрузки истории;
- mutation отметки прочтения.

### Локальное состояние

В `useState` находятся:

- выбранная беседа;
- загруженные сообщения;
- pending-сообщения;
- состояние соединения;
- множество online user IDs;
- loading-флаги;
- последняя ошибка.

### Почему используются `useRef`

Обработчики Socket.IO живут долго и могут замкнуть старые значения state. Поэтому:

- `selectedIdRef` всегда содержит актуальную выбранную беседу;
- `messagesRef` всегда содержит актуальную историю;
- `socketRef` хранит текущее соединение.

### Отправка сообщения

`sendMessage` выполняет следующие шаги:

1. Создаёт уникальный `clientMessageId`.
2. Сохраняет команду в IndexedDB outbox.
3. Мгновенно добавляет pending-сообщение в интерфейс.
4. Вызывает `sendCommand`.
5. `sendCommand` отправляет Socket.IO event `message:send`.
6. После успешного ack сообщение переносится из pending в обычную историю.
7. Запись удаляется из IndexedDB.

Если сеть пропала, команда остаётся в outbox и может быть отправлена повторно.

### Восстановление после reconnect

После нового подключения hook:

1. ставит состояние `synchronizing`;
2. запрашивает сообщения после последнего известного `sequence`;
3. повторяет команды из outbox;
4. обновляет список бесед;
5. переключается в `online`.

### Отметка прочтения

Беседа отмечается прочитанной, только когда вкладка видима.

- При активном socket используется `read:update`.
- Без socket используется HTTP `POST /read`.
- При возвращении на вкладку срабатывает `visibilitychange`.

## 9. Services клиента

### `services/api/messenger/index.ts`

Это единое описание HTTP API через RTK Query.

В нём находятся:

- query — чтение данных;
- mutation — изменение данных;
- `transformResponse` — извлечение DTO из server response;
- tags — правила инвалидирования cache.

Пример логики cache:

```text
createGroup mutation
    ↓
invalidates ConversationList
    ↓
RTK Query повторно получает список бесед
    ↓
sidebar обновляется
```

RTK Query здесь отвечает за HTTP и cache. Realtime-события остаются в Socket.IO.

### `services/realtime/socket.ts`

Создаёт Socket.IO client со следующими настройками:

- cookie отправляется через `withCredentials`;
- сначала используется WebSocket, затем fallback polling;
- включён reconnect с увеличивающейся задержкой;
- `autoConnect: false`, чтобы handlers были зарегистрированы до подключения.

### `services/storage/outbox.ts`

Работает с IndexedDB браузера.

Outbox — очередь команд, которые пользователь уже создал, но сервер ещё не подтвердил. Она нужна, чтобы сообщение не исчезло при кратком обрыве сети или перезагрузке страницы.

Операции:

- `saveOutboxCommand`;
- `removeOutboxCommand`;
- `listOutboxCommands`.

## 10. Типы и utilities клиента

### `types/messenger.ts`

Содержит DTO и локальные типы:

- `User`;
- `Conversation`;
- `Member`;
- `Message`;
- `PendingMessage`;
- `OutboxCommand`;
- Socket ack-типы.

DTO клиента должны соответствовать DTO, которые возвращает сервер.

### `utils/messages.ts`

Безопасно объединяет массивы сообщений, убирая дубли и сохраняя порядок по `sequence`.

### `utils/readReceipt.ts`

Вычисляет состояние галочек по `lastReadSequence` участников беседы.

### `utils/linkify.ts`

Разбивает текст на обычные части и web-ссылки. Это чистая функция, поэтому её легко тестировать без React.

### `utils/format.ts`

Форматирует время сообщения, дату разделителя и время в sidebar.

### `utils/apiError.ts`

Превращает разные варианты ошибок RTK Query в понятную строку для пользователя.

## 12. Запуск и сборка сервера

### `server/src/index.ts`

Минимальная точка входа:

1. читает config;
2. вызывает `buildApp`;
3. запускает Fastify;
4. обрабатывает `SIGINT` и `SIGTERM`;
5. корректно закрывает Socket.IO и SQLite.

### `server/src/app.ts`

Это composition root — место, где создаются и связываются зависимости.

Порядок примерно такой:

```text
Fastify
  + cookie
  + CORS
  + SQLite
  + repositories
  + Socket.IO
  + services
  + auth hooks
  + routes
  + graceful close
```

`app.ts` не должен содержать SQL или бизнес-правила. Он только собирает приложение.

### `server/src/config.ts`

Читает `.env` и проверяет его через Zod.

Основные настройки:

- `HOST` — адрес сервера;
- `PORT` — HTTP и Socket.IO port;
- `CLIENT_ORIGIN` — разрешённый origin клиента;
- `DATABASE_PATH` — путь к SQLite;
- `DEV_AUTH_ENABLED` — локальный dev-login;
- `SESSION_SECRET` — подпись cookie;
- `MESSAGE_MAX_LENGTH` — лимит сообщения.

## 13. Одинаковая архитектура feature-модулей

Модули `conversations` и `messages` разделены одинаково:

```text
*.routes.ts       HTTP: получить request, вернуть response
*.schemas.ts      Zod: проверить входные данные
*.service.ts      бизнес-правила и сценарии
*.repository.ts   SQL и транзакции
*.types.ts        DTO, rows и команды
*.mapper.ts       преобразование SQLite row → DTO
```

### Route

Route знает про HTTP-коды, параметры URL и тело запроса. Он не должен писать SQL.

### Schema

Schema не доверяет входным данным. Даже если клиент написан нами, любой запрос можно отправить вручную.

### Service

Service содержит правила предметной области. Например, `MessageService`:

- обрезает пробелы;
- проверяет длину;
- вызывает repository;
- публикует событие только для нового сообщения.

### Repository

Repository — единственный слой feature-модуля, который знает структуру таблиц и SQL.

Он отвечает за:

- запросы;
- транзакции;
- ограничения доступа на уровне данных;
- преобразование строк БД в DTO.

## 14. База данных

Файл рабочей БД:

```text
server/data/ems-messenger.sqlite
```

Рядом могут появляться:

- `ems-messenger.sqlite-wal` — журнал новых изменений;
- `ems-messenger.sqlite-shm` — служебная shared-memory информация WAL.

Это нормальные рабочие файлы SQLite. Не нужно удалять их у запущенного сервера.

### Таблицы

#### `users`

Локальные пользователи: login, имя, цвет аватара и статус.

#### `external_identities`

Заготовка для связи локального пользователя с внешней системой идентификации.

#### `conversations`

Личные и групповые беседы.

Важные поля:

- `type` — `DIRECT` или `GROUP`;
- `direct_key` — уникальная пара пользователей для DIRECT;
- `next_message_sequence` — следующий порядковый номер сообщения;
- `status` — активная или удалённая беседа.

#### `conversation_members`

Связь пользователей и бесед.

Важные поля:

- `role` — владелец или участник;
- `visible_from_sequence` — с какого сообщения участник видит историю;
- `last_read_sequence` — до какого сообщения он прочитал;
- `left_at` — вышел ли пользователь.

#### `messages`

Сохранённые сообщения.

Важные поля:

- `client_message_id` — ID, созданный клиентом;
- `sequence` — порядок внутри беседы;
- `body` — текст;
- `created_at` — время сервера.

Уникальность `(sender_id, client_message_id)` защищает от дубля при повторной отправке.

## 15. Миграции

```text
server/src/database/migrations/
├── 001-initial-schema.ts
├── 002-message-interactions.ts
├── 003-pins-and-forwards.ts
├── 004-pin-notification-links.ts
├── index.ts
└── migration.types.ts
```

Миграция — точное версионированное изменение схемы БД. Поэтому внутри неё находится обычный SQL. Это правильное место для SQL.

Таблица `schema_migrations` хранит уже применённые версии. При запуске сервер применяет только новые.

Правило развития:

- не редактировать уже применённую `001`;
- каждое следующее изменение добавлять новым файлом с очередным номером;
- зарегистрировать новую миграцию в `migrations/index.ts`;
- проверить upgrade на существующей БД.

## 17. Авторизация сейчас

Текущая авторизация — локальная демонстрационная.

1. `DevLogin` получает список тестовых пользователей.
2. `POST /api/v1/dev/session` записывает подписанную cookie.
3. Auth hook читает cookie перед защищённым route.
4. В `request.currentUserId` записывается ID активного пользователя.
5. Socket.IO handshake читает ту же cookie.

Public routes явно помечены `config: { public: true }`.

Также сервер проверяет `Origin`: браузерный запрос должен прийти от разрешённого клиента.

Это удобно для локальной демонстрации, но не является будущей интеграцией с EMS-аутентификацией.

## 18. Realtime и Socket.IO

### Rooms

Сервер использует комнаты:

- `user:<userId>` — все вкладки одного пользователя;
- `conversation:<conversationId>` — активные участники беседы.

Клиент не выбирает комнаты самостоятельно. Сервер добавляет socket только после проверки cookie и membership.

### События от клиента

- `message:send` — отправить сообщение;
- `read:update` — обновить прочитанную последовательность.

### События от сервера

- `connection:ready` — подключение принято;
- `message:new` — новое сохранённое сообщение;
- `message:updated` — изменились реакции или закрепление;
- `conversation:updated` — беседа изменилась;
- `membership:updated` — пользователь добавлен или удалён;
- `read:updated` — изменилось прочтение;
- `presence:snapshot` — полный список online при подключении;
- `presence:updated` — один пользователь вошёл или вышел.

Звонки используют отдельные события `call:*` и `group-call:*`: сервер проверяет membership и занятость, но передаёт только WebRTC-сигнализацию, а не медиапоток.

## 19. Presence: online/offline

`PresenceRegistry` хранит не boolean, а количество активных соединений пользователя.

Это важно: один пользователь может открыть две вкладки.

```text
первая вкладка подключилась   count 0 → 1   пользователь стал online
вторая вкладка подключилась   count 1 → 2   статус не меняется
первая вкладка закрылась      count 2 → 1   пользователь ещё online
вторая вкладка закрылась      count 1 → 0   пользователь стал offline
```

Presence сейчас хранится в памяти одного backend-процесса. Для нескольких серверных instances понадобился бы общий broker, например Redis.

## 19.1. Личные аудио- и видеозвонки

Звонки работают через WebRTC. Аудио и видео идут напрямую между браузерами; Fastify/Socket.IO передаёт только служебные сигналы.

Клиентский `useDirectCall` отвечает за:

- запрос доступа к микрофону и камере;
- создание `RTCPeerConnection`;
- SDP offer/answer;
- обмен ICE-кандидатами;
- локальный и удалённый `MediaStream`;
- mute, camera off и завершение;
- очистку media tracks и peer connection.

Серверные `CallRegistry` и call handlers отвечают за:

- звонки только внутри DIRECT;
- проверку membership и online-состояния;
- запрет второго одновременного звонка для занятого пользователя;
- маршрутизацию offer, answer и ICE;
- освобождение звонка при отказе, завершении или offline.

После завершения сервер создаёт сохраняемое сообщение от имени инициатора звонка:

- `📞 Звонок завершён · 03:17` — если на звонок ответили;
- `📞 Звонок отменён` — если инициатор завершил вызов раньше ответа;
- `📞 Звонок отклонён` — если собеседник нажал «Отклонить»;
- `📞 Пропущенный звонок` — если вызываемый пользователь отключился во время вызова.

Это обычное persisted-сообщение: оно получает `sequence`, участвует в unread/read receipts, доставляется через `message:new` и остаётся в SQLite после перезапуска.

Основные call events:

- `call:start` / `call:incoming`;
- `call:answer` / `call:answered`;
- `call:ice`;
- `call:reject` / `call:rejected`;
- `call:end` / `call:ended`.

Текущая версия рассчитана на один backend instance и локальные сети. Для production-соединений через NAT понадобятся STUN/TURN, а состояние звонков для нескольких backend instances нужно вынести в общий broker/storage.

## 20. Полный путь отправки сообщения

Это главный сценарий для понимания архитектуры.

```text
MessageComposer
  ↓ onSend(body)
MessengerWorkspace
  ↓ messenger.sendMessage(body)
useMessenger
  ↓ IndexedDB outbox
  ↓ socket.emit('message:send')
registerSocketHandlers
  ↓ MessageService.send()
MessageRepository.append()
  ↓ SQLite transaction
EventPublisher.messageCreated()
  ↓ room conversation:<id>
socket event 'message:new'
  ↓
useMessenger.completeMessage()
  ↓
MessageList перерисовывается
```

Сервер отправляет ack и realtime-событие только после успешного commit в SQLite.

## 21. Прочитанные сообщения

У каждого участника есть `lastReadSequence`.

Если пользователь прочитал сообщение с sequence `15`, это означает, что прочитаны все доступные ему сообщения до `15` включительно.

Значение обновляется монотонно: оно может только увеличиваться. Старый или повторный запрос не уменьшит прогресс прочтения.

Клиент сравнивает sequence собственного сообщения с `lastReadSequence` других участников и выбирает состояние галочки.

## 28. Устойчивость и синхронизация

После регрессионного аудита в проекте закрыты следующие сценарии:

- Socket.IO-комана без ACK или с ACK неверного типа не может завершить backend-процесс;
- `message:new` и `message:updated` публикуются по персональным user rooms только активным участникам, которым доступен `sequence` сообщения;
- preview старого ответа или недоступной пересылки скрывается для конкретного получателя;
- каждая асинхронная загрузка истории привязана к `conversationId` и поколению выбора, поэтому поздний ответ из другого чата отбрасывается;
- reconnect загружает весь пропущенный диапазон страницами по 100 сообщений и не перескакивает через realtime-сообщение с большим `sequence`;
- outbox повторяется последовательно, с ограниченным exponential backoff; постоянный отказ блокирует автоповтор до ручной команды;
- обычная отправка и пересылка используют одинаковую очередь IndexedDB;
- запрещённый выход владельца или выход из DIRECT не меняет историю и `sequence`; успешный выход и системное сообщение сохраняются в одной транзакции;
- исключение из группы сразу отзывает доступ к групповому звонку и закрывает peer connection штатного клиента;
- звонок привязан к конкретной Socket.IO-вкладке, завершается при обрыве и не блокирует новый вызов; дозвон без ответа завершается через 30 секунд;
- групповое видео не воспроизводит remote audio второй раз через скрытый `<audio>`;
- при догрузке старой истории `MessageList` сохраняет позицию, а новое сообщение не перебрасывает вниз читающего архив пользователя.

Для списка бесед `listForUser` теперь пакетно загружает участников, unread count и последние сообщения. Число SQL-выборок больше не растёт по формуле `1 + 3N`. Клиент обновляет затронутую беседу в RTK Query cache без полного refetch на каждое сообщение. Полная сверка сохранена для membership/read/reconnect-событий.

- продвинутый полнотекстовый индекс поиска;

## 30. Главное, что стоит запомнить

1. React-компонент не должен напрямую писать в БД.
2. RTK Query отвечает за HTTP и cache.
3. Socket.IO отвечает за события в реальном времени.
4. `useMessenger` координирует клиентский сценарий.
5. Route принимает HTTP, service содержит правила, repository работает с SQL.
6. Событие публикуется только после сохранения данных.
7. `clientMessageId` защищает повторную отправку от дублей.
8. `sequence` задаёт порядок сообщений внутри беседы.
9. IndexedDB outbox хранит неподтверждённые команды клиента.
10. Миграции описывают историю схемы и не должны переписываться задним числом.
